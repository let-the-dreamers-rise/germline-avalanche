How you use it

Three things from you. Two from the chain.

  1. 01

    Say what can vary

    List the settings you actually tune: numbers, switches, choices.

  2. 02

    Plug in the eval you already have

    A scored test set, a shadow replay, an LLM judge. Germline only needs a score.

  3. 03

    Run it, get a better config

    With the random control built in, so you know whether the search earned its keep.

  4. 04

    Each child is committed before its dice exist

    The seed comes from a block that has not been mined yet. Nobody can shop for a flattering result.

  5. 05

    Anyone re-checks it

    One command, no key, no gas: GENUINE or FORGED, from public chain data.

const trial = defineTrial({
  name: "support-agent",
  genes: {
    retrievalDepth: { type: "int", min: 1, max: 12 },
    rerank: { type: "bool" },
    temperature: { type: "choice", options: [0, 0.3, 0.7] },
  },
  evaluate: async (config) => ({
    score: await runEvalSet(config),
  }),
});

// Germline never needs to know what your
// system does, only how to score it.
const run = await search(trial, { budget: 40 });

run.best.config     // ship this
run.verdict.winner  // 'search' | 'random' | 'tied'
run.baseline.median // what random got on the same budget
// TX 1: commit to breeding at a future block
requestSpawn(parentId)
blockhash(requestBlock)  // does not exist yet

// TX 2: reveal, afterwards
seed = keccak256(parentRoot, blockhash(requestBlock),
                 parentId, ordinal)

Score with an LLM judge

makeJudge() turns a model into your evaluate(). Fitness may be judged by a model; heredity never is.

Show a customer which version shipped

A vendor’s own dashboard is not evidence. A lineage they can re-check themselves is.

Selection is enforced

Below the survival threshold a config leaves no descendants. The contract will not mint a child its parent has not earned.

Questions

The parts people ask about first.

What do the scores mean?

A score is whatever your own eval returns for a configuration, shown as a percentage. Higher is better. On chain it is stored in basis points, so 3148 means 31.48%.

Does my data leave my machine?

No. Your eval runs where it runs today. When you turn on provenance, the chain stores a 32-byte hash of each configuration and its score; the configurations themselves stay with you. Nothing sits in your request path.

Do I need a wallet or crypto to use it?

No. The search runs entirely locally. A team can try it in a minute with no wallet and turn on provenance later, when they need to show someone.

Is it a better optimiser than random search?

Not always, and it says so. On a small space where you can sample a fifth of everything, random wins. On a real space sampled under one percent, selection is ahead. search() runs the random control by default and reports the winner.

Why involve a chain at all?

So that the customer verifies the record themselves rather than trusting the vendor who produced it. The seed for each child comes from a block that did not exist when the breeder committed, which is something only a chain can supply.

What does a GENUINE verdict actually prove?

Where a configuration came from: which parent, which random seed, and that the seed was fixed by a block that did not exist yet, so nobody could pick a lucky one. And that the claimed score is the score your eval really gives. It does not prove your eval measures the right thing. That part is yours.

What is not done yet?

The curator role is centralised, an attestor is trusted to report honestly (dishonesty is detectable afterwards, not prevented), and fitness comes from one trial. C-Chain mainnet is next. The README lists every limitation.
